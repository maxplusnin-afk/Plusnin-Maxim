# BRIEF: CarLog — учёт автомобиля и пробега

## 1. Общие сведения

**Название продукта:** CarLog

**Краткое описание:**
CarLog — десктопное приложение для ведения истории эксплуатации личного автомобиля. Позволяет фиксировать пробег, заправки, замену масла и других расходников, а также напоминает о скором техническом обслуживании. Решает проблему забытых дат ТО.

**Целевая аудитория:**
- Владельцы личных автомобилей, которые хотят контролировать расходы и вовремя проходить ТО.
- Студенты и молодые водители, купившие первую машину и не имеющие опыта ведения учёта.
- Автолюбители, которые хотят видеть статистику: расход топлива, стоимость километра, затраты за месяц.

## 2. Функциональные требования

### Обязательные (MVP)

- Пользователь может **добавить автомобиль** с указанием марки, модели, года выпуска, госномера и текущего пробега.
- Пользователь может **просмотреть список своих автомобилей** и выбрать активный.
- Пользователь может **добавить запись о заправке**: дата, пробег, количество литров, цена за литр, тип топлива.
- Пользователь может **добавить запись о техническом обслуживании**: дата, пробег, тип работ (замена масла, фильтров, шин и т.д.), стоимость.
- Пользователь может **просмотреть историю всех записей** по автомобилю в виде таблицы (сортировка по дате и пробегу).
- Пользователь может **редактировать и удалять** записи (с подтверждением).
- Пользователь может **видеть текущий пробег** автомобиля (рассчитывается по последней записи).
- Пользователь может **получать напоминание** о скором ТО (например, если до следующей замены масла осталось менее 500 км или 30 дней).

### Дополнительные

- Пользователь может **видеть статистику**: средний расход топлива, суммарные затраты за месяц/год, стоимость километра.
- Пользователь может **экспортировать историю** в CSV или текстовый файл.
- Пользователь может **добавлять несколько автомобилей** и переключаться между ними.
- Пользователь может **строить график** изменения расхода топлива или пробега.
- Пользователь может **задавать собственный интервал ТО** (например, каждые 10 000 км).

## 3. Нефункциональные требования

- **Язык интерфейса:** русский.
- **Производительность:** время отклика интерфейса — не более 1 секунды при стандартных операциях (открытие списка записей, сохранение заправки, расчёт статистики).
- **Хранение данных:** локально в файле БД (SQLite), сеть не используется.
- **Защита от ошибок:**
  - нельзя сохранить запись с пробегом меньше предыдущего значения по этому автомобилю;
  - нельзя указать отрицательное или нулевое количество литров и цену;
  - нельзя удалить автомобиль, если у него есть записи, без подтверждения;
  - нельзя указать дату заправки в будущем;
  - нельзя сохранить запись без выбранного автомобиля.
- **Инициализация БД:** при первом запуске приложение само создаёт таблицы из встроенного SQL-скрипта и добавляет справочник типов работ (замена масла, фильтров и т.д.).

## 4. Модель данных (ER-диаграмма)

### Таблицы и поля

**Таблица `cars` (Автомобили)**

| Поле | Тип | Ключ | Описание |
|------|-----|------|----------|
| id | INTEGER | PK | Идентификатор автомобиля |
| brand | TEXT | | Марка |
| model | TEXT | | Модель |
| year | INTEGER | | Год выпуска |
| plate_number | TEXT | | Госномер |
| initial_mileage | INTEGER | | Пробег при добавлении |
| created_at | DATETIME | | Дата добавления |

**Таблица `fuel_types` (Типы топлива)**

| Поле | Тип | Ключ | Описание |
|------|-----|------|----------|
| id | INTEGER | PK | Идентификатор |
| name | TEXT | | Название (АИ-92, АИ-95, ДТ, газ) |

**Таблица `maintenance_types` (Типы работ)**

| Поле | Тип | Ключ | Описание |
|------|-----|------|----------|
| id | INTEGER | PK | Идентификатор |
| name | TEXT | | Название (замена масла, фильтров, шин и т.д.) |
| default_interval_km | INTEGER | | Интервал по умолчанию (км) |
| default_interval_days | INTEGER | | Интервал по умолчанию (дней) |

**Таблица `fuel_records` (Заправки)**

| Поле | Тип | Ключ | Описание |
|------|-----|------|----------|
| id | INTEGER | PK | Идентификатор записи |
| car_id | INTEGER | FK | Ссылка на автомобиль |
| fuel_type_id | INTEGER | FK | Ссылка на тип топлива |
| date | DATE | | Дата заправки |
| mileage | INTEGER | | Пробег на момент заправки |
| liters | REAL | | Количество литров |
| price_per_liter | REAL | | Цена за литр |
| total_cost | REAL | | Итоговая стоимость (расчётная) |

**Таблица `maintenance_records` (ТО и ремонт)**

| Поле | Тип | Ключ | Описание |
|------|-----|------|----------|
| id | INTEGER | PK | Идентификатор записи |
| car_id | INTEGER | FK | Ссылка на автомобиль |
| maintenance_type_id | INTEGER | FK | Ссылка на тип работ |
| date | DATE | | Дата выполнения |
| mileage | INTEGER | | Пробег на момент ТО |
| cost | REAL | | Стоимость |
| comment | TEXT | | Комментарий |

### Связи

- `cars` 1:N `fuel_records` — у одного автомобиля много записей о заправках.
- `cars` 1:N `maintenance_records` — у одного автомобиля много записей о ТО.
- `fuel_types` 1:N `fuel_records` — один тип топлива используется во многих заправках.
- `maintenance_types` 1:N `maintenance_records` — один тип работ используется во многих записях ТО.

### Обоснование нормализации

Данные разнесены по таблицам для устранения дублирования: типы топлива и типы работ хранятся в справочниках, а не строкой в каждой записи. Это позволяет менять название типа в одном месте и избегать опечаток. Заправки и ТО вынесены в отдельные таблицы, так как имеют разные наборы полей. Автомобили выделены в отдельную сущность — это позволяет в будущем вести учёт по нескольким машинам.

## 6. Сценарии использования (Use Cases)

### Сценарий 1: Добавление заправки

**Актёр:** Пользователь

**Предусловие:** В системе есть хотя бы один автомобиль, открыто главное окно.

**Основной поток:**
1. Пользователь нажимает кнопку «Добавить заправку».
2. Система открывает форму добавления заправки.
3. Пользователь выбирает дату, вводит пробег, выбирает тип топлива, указывает литры и цену за литр.
4. Система автоматически рассчитывает итоговую стоимость.
5. Пользователь нажимает «Сохранить».
6. Система проверяет корректность данных (пробег больше предыдущего, литры > 0, цена > 0, дата не в будущем).
7. Система сохраняет запись в БД.
8. Система закрывает форму и обновляет сводку на главном экране.

**Альтернативный поток:**
- Если пробег меньше предыдущего значения — система показывает ошибку «Пробег не может быть меньше предыдущего (XXXXX км)».
- Если дата в будущем — система показывает ошибку «Дата не может быть в будущем».

---

### Сценарий 2: Добавление записи о ТО

**Актёр:** Пользователь

**Предусловие:** В системе есть хотя бы один автомобиль.

**Основной поток:**
1. Пользователь нажимает «Добавить ТО».
2. Система открывает форму.
3. Пользователь выбирает тип работ (замена масла, фильтров и т.д.), дату, пробег, стоимость, при необходимости — комментарий.
4. Пользователь нажимает «Сохранить».
5. Система проверяет данные и сохраняет запись.
6. Система пересчитывает дату следующего ТО на основе интервала типа работ.
7. Система обновляет блок напоминаний.

**Альтернативный поток:**
- Если тип работ не выбран — система показывает ошибку.
- Если пробег меньше предыдущего — система показывает ошибку.

---

### Сценарий 3: Просмотр напоминаний о ТО

**Актёр:** Пользователь

**Предусловие:** В системе есть записи о ТО с заданными интервалами.

**Основной поток:**
1. Пользователь открывает главное окно.
2. Система рассчитывает, сколько км и дней осталось до следующего ТО по каждому типу работ.
3. Система отображает напоминания, если осталось менее 500 км или менее 30 дней.
4. Пользователь видит список напоминаний.

**Альтернативный поток:**
- Если напоминаний нет — блок показывает «Всё в порядке, ТО не требуется».

---

### Сценарий 4: Просмотр статистики

**Актёр:** Пользователь

**Предусловие:** В БД есть минимум две заправки.

**Основной поток:**
1. Пользователь нажимает «Статистика».
2. Система рассчитывает средний расход топлива (л/100 км), суммарные затраты, стоимость километра.
3. Система строит график расхода по заправкам.
4. Пользователь просматривает данные.

**Альтернативный поток:**
- Если записей недостаточно — система показывает сообщение «Недостаточно данных для расчёта статистики».
